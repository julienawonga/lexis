# Audit of the engine and the frontend (2026-11-16)

A read-only audit of `main` at `2a3a9e2f` and of the maintainer's running stack.
No code was changed, nothing was restarted, and no question was sent to the
model. It lists what stands between Lexis and "operational", each limit with its
evidence, its severity and the cost of fixing it.

## How to read this

- **Method.** Three code reviews (frontend journeys, operations and security,
  the text-to-SQL pipeline) plus read-only probes of the running stack
  (`curl`, `docker logs`, `docker inspect`). Every finding rated HIGH or
  CRITICAL was re-read in the code by a second reader.
- **Evidence kinds.** `CODE`: the path was read end to end, nothing was run.
  `LIVE`: observed on the running stack on 2026-11-16. `MEASURED`: an entry of
  [experiments.md](./experiments.md). A `CODE` finding says the defect exists in
  the code; it does not say how often a user meets it.
- **Severity.** CRITICAL: a wrong number can reach the user with nothing to
  warn them, or a security hole on a default install. HIGH: a main journey
  fails, lies or hides a failure. MEDIUM, LOW: the rest.
- **Cost.** S under two hours, M half a day, L more than a day. **Gate** marks a
  fix that changes what the model sees, so it must pass the evaluation gate of
  `CLAUDE.md` (an `ACCEPT`) before merging.
- **What this audit is not.** No browser was opened, no load was applied, the
  install path was read and not executed, and nothing here comes from a
  company's own data. Those are phase 1 work or outside reach (see the end).

## Engine

### E1. No way to refuse (CRITICAL; L, gate)

- **Limit.** A question the schema cannot answer ends as a refusal only when
  retries run out, never by a decision. Measured: 21 of 28 runs on unanswerable
  questions returned a result for a different question, 10 of them with no
  warning at all (`MEASURED`, E27).
- **Cause (`CODE`).** The generation output requires non-empty SQL
  (`retrieval/text_to_sql/models.py:239`, `sql_code: NonEmptyStr`) and the
  prompt has no "cannot answer" outcome. The static validator rejects the honest
  empty forms and asks for "a real query"
  (`agents/sql_parse_validation.py:232`, `:908`), but only when every projected
  column is a constant, so a real column next to a `NULL` stand-in passes.
  Retrieval has no distance floor, so every question finds a nearest
  neighbour. Nothing deterministic compares the question's entities with the
  schema. When the engine does give up, the user reads a generic sentence with
  no reason (`agents/sql_unconstructable.py:67`).
- **Already tried.** The model's self-assessment flagged 52% of answerable
  questions (E27, rejected). A rule on the SQL text caught 36% (E29,
  exploratory).
- **Fix.** A deterministic check of the question's entities against the schema
  and the ontology, plus an explicit refusal outcome in generation. It changes
  what the model sees and needs a frozen unanswerable set first (see V1).

### E2. The chart recomputes the numbers (CRITICAL for non-additive measures; S)

- **Limit.** The chart is not a picture of the result: it drops rows that hold a
  NULL, groups by the x column and **sums**
  (`visualization/chart_specs.py:171`, `:186`, `:223`). If the SQL returned an
  average, a ratio or a percentage with a repeated x value, the chart shows a
  sum of averages. A unit test pins the summing as intended
  (`tests/test_chart_specs.py:27`).
- **Also.** The chart is built from the row-capped result, and keeps at most 60
  rows (`chart_specs.py:20`); it does say so ("Top N of M rows" subtitle), a
  point this audit first got wrong and corrected on 2026-11-16 after reading
  the code again. Decimals become floats in the result JSON
  (`agents/sql_execution.py:189`), so very large or very precise values lose
  digits.
- **Evidence.** `CODE`, plus a local pandas check of the Decimal conversion.
  How often the model picks a repeated x for a non-additive measure was not
  observed.
- **Fix.** Draw the rows as returned when x is unique; otherwise show the table.
  Chart code only: no gate.

### E3. Validation fails open, silently (HIGH; S to mark, M to close)

Four separate paths let SQL through that no check accepted, and none leaves a
structured mark on the answer (`CODE` for all).

1. **The intent check passes on failure.** A model error, an empty reply, or
   "invalid" with no listed issue all return `valid_sql`
   (`agents/sql_parse_validation.py:1107`, `:1120`, `:1139`). A gateway outage
   turns the check off without a word.
2. **Soft checks stop counting after five attempts.** The join-path, JSONB,
   empty-`LIKE` and value-repair checks are ignored past
   `INTENT_VALIDATION_SKIPPED_AFTER = 5` (`text_to_sql_graph.py:157`).
3. **An exception in a step is swallowed.** `handle_error` returns the state
   unchanged (`base.py:94-128`); only the execution step sets a failure
   decision. If the validation step raises, the previous decision stands and
   the router sends the SQL on to execution (`text_to_sql_graph.py:105-124`).
   The read-only guard still applies.
4. **The oscillation fallback returns the candidate that broke the evidence
   rules.** `_best_rejected_candidate` prefers the SQL rejected only for
   contradicting the evidence, which includes certified definitions
   (`sql_parse_validation.py:783`). The caveat is a sentence appended to the
   prose (`agents/response.py:81`); the answer has no caveat field, and the flag
   `returned_deterministic_fallback` is set and never read.
   `MEASURED`: of 21 substituted answers in E27, 11 carried this note.

- **Fix.** First make every one of these visible: a structured `caveats` list on
  the answer and a notice in the interface (S to M, no gate). Deciding whether
  each should fail closed changes answers and needs the gate.

### E4. The row cap is told in prose only (HIGH; S)

`result_truncated_at` is in the answer (`agents/response.py:95`) but the web app
does not read it (`frontend/lib/answerMessages.ts:65`), the table and chart
message carries no flag, and it is not stored with the conversation
(`server/chat/conversation_dal.py:189`). A user who totals a capped table, or
reads the chart, has only a sentence in the text to warn them. Non-Postgres
connectors also fetch the whole result before trimming it. `CODE`.

### E5. The database is chosen on thin evidence and never named (HIGH with several databases; S to show, M gate to change)

With no database selected, the "vote" has no minimum evidence and no margin
between the first two candidates (`agents/candidates_retrieval.py:145`). The
choice appears only in a log line (`:660`). `MEASURED`: E31 saw a wrong
database chosen on one weak hit. Showing "answered from database X" under each
answer is cheap and needs no gate.

### E6. An empty result is pushed toward a non-empty one, and "no rows" is never said (HIGH when zero is the true answer; S for the notice)

On an empty result the engine tells the model it is "asking the wrong question
of the data" and to prefer other tables
(`agents/empty_result_value_repair.py:49-70`). If the second try is also empty
it passes with no note (`:131`). The text shown was written before execution, so
it never says that nothing was found. `CODE`; the rate is not measured.

### E7. Time budgets add up to far more than the 300 s limit (HIGH; M)

One model call may take 3 attempts of 120 s, then a fallback model; generation
retries 3 times; up to 7 reconstructions; then a second full attempt
(`utils/llm_invoke.py:48-49`, `agents/sql_from_semantic.py:382`,
`text_to_sql_graph.py:86`, `main.py:83`). Nothing shares one deadline. A slow
but valid query that hits the 30 s statement timeout is handed back to the
model to rewrite. `MEASURED` symptom: runs cancelled at 300 s in E20, E22, E27.
That these budgets cause them is a reading of the code, not a per-run
measurement.

### E9. Constants set on public benchmarks

The owner's rule is that no constant is tuned on a public set without saying
so. These already are, by their own comments (`CODE`): the relevance filter's
column cut (25) and bypass size (2) cite BIRD dev
(`agents/candidates_preparation.py:105-132`); the hub-sibling caps (6, 30) cite
an earlier benchmark run (`:140-146`); the dialect rules cite Spider2
(`prompts.py:310`); the Term-definition settings rest on one LiveSQLBench run
for the whole feature, not per knob. The clarification thresholds are declared
"not tuned yet" (`clarification.py:72-78`). Most other limits (7
reconstructions, 5 skipped checks, 300 s, 10,000 rows, 30 s) carry no
rationale at all. None of them has been checked on a company's data.

## Operations and security

### O1. Unauthenticated API by default, never tried with the token (HIGH; S)

- `LIVE`: with no credentials, `GET /api/connections` returned the 20
  registered connections (host, port, user, database name; **no password**) and
  `GET /api/terms` returned every Term. All 66 routes, including
  `POST /api/connections`, `POST /api/semantic-compilation/reset` and
  `POST /api/model/import`, accept any local caller. `/docs` and
  `/openapi.json` are served too.
- `CODE`: the token is commented out in `.env.example:120`; without it the
  middleware passes everything and the forwarded user identity header is
  trusted from anyone (`server/internal_auth.py:127`, `server/identity.py:28`).
- Limited on this machine because the backend listens on localhost only. The
  token path itself is `FAKES` in the register: no stack has ever run with it.
- **Fix.** Set a token and restart (needs the owner's go-ahead), then try the
  401 path, the web app, ingestion and the eval harness for real.

### O2. No backup, restore or rollback procedure (HIGH; M)

`CODE`/docs: the only mention of a dump is one line in `HANDOFF.md`. Nothing
says which schemas matter (`public`, `vdb`, `frontend`), how to restore, or how
to roll back an image: an older image refuses to start on a newer database and
its message advises `alembic upgrade head`, the wrong direction
(`dal/schema_version.py:81`). The web app's schema is applied with
`prisma db push`, which has no way back, and its migration script truncates a
table without a backup (`frontend/prisma/migrate.sh:36-56`).

### O3. Health checks see Postgres and nothing else (HIGH; M)

`CODE`: `/api/health` checks Postgres and the Alembic revision
(`server/health/checks.py:27-52`); the chat worker entry is a counter. Health
stays green with an invalid model key, a wrong embedding endpoint, an empty
index or a chat worker that cannot start. Model settings are validated lazily,
at the first call (`utils/model_config.py:60`). Not reproduced: a worker that
fails at start appears to produce an answer stream that ends empty, with no
error (`server/chat/worker.py:391-405`, `:508`); to confirm in phase 1.

### O4. Install from scratch: traps, and nothing ever runs the images (HIGH; M)

- `CODE`: `.env.example` ships the embedding and rerank endpoints uncommented
  with placeholder values (`:80-81`, `:98-100`); they override the default
  model settings, and the README quickstart does not mention them. A literal
  install sends embeddings to a placeholder; the index is then empty and chat
  falls back to the raw schema with only a log line.
- The README builds with `docker compose up -d --build`; the maintainer's notes
  say that building next to the running stack crashes the Docker VM on this
  machine.
- CI builds both images and never starts them (`ci-python.yml:74-83`,
  `ci-client.yml:97-107`); the release workflow has never run.
- The admin seed can fail with only a console line while the web app reports
  healthy, and it **resets the admin password to the `.env` value at every
  start** (`frontend/auth/seed-admin.ts:60-74`).

### O5. Source-database passwords are stored unencrypted (HIGH; L)

Documented, not hidden (`docs/connections.md:39`): unless Vault is configured,
the credentials of every connected database sit as JSON in the catalog
(`dal/schema.py:184`). Any dump or pgAdmin session exposes them. A Vault outage
makes connections vanish silently (`connectors/vault.py:94-108`).

### O6. Agent SQL: read-only and capped on the main paths, with two exceptions

`CODE`: every execution path was listed. Chat, the clarification coordinator,
the probes and the value index go through the parse-time guard, the
database-enforced read-only mode where the engine has one, and the row cap.
No route executes SQL sent by a client. Exceptions:

- **Prediction path (Kumo).** Model-written SQL runs through the raw connector
  with no guard, no read-only mode, no cap (`retrieval/kumo/pql_gen.py:1198`).
  Off unless `KUMO_RFM_API_KEY` is set; `LIVE`: unset on this stack. HIGH if
  enabled; M.
- **Snowflake, Databricks, Kyuubi, HeavyDB** have only the parse-time guard
  (known, roadmap step 11). The guard has never been cross-checked against a
  real engine (`FAKES` in the register).

### O7. Load (not measured in this audit)

`CODE`: 4 concurrent chats, then a wait of 120 s, then 503. Not bounded: the
number of waiting requests, worker memory, open streams, and ingestion (each
`POST /ingest` starts a thread with no lock, `ingestion_service/ingest.py:208`,
and each ingestion pays for embeddings). A worker that hangs while starting
holds its slot with no timeout (`server/chat/worker.py:508`). The 8-chat run on
the final code is still to do (`FAKES` in the register); it needs the owner's
go-ahead and about 8 questions' worth of model calls.

### O8. Errors and logs (MEDIUM; S to M)

`CODE`: no exception handler is registered, so an unexpected error is a
plain-text 500; no request id; no log-level setting. `LIVE`: expected errors
are clear JSON (404 `Term not found`, 422 with the missing field). Every chat
request body is logged at INFO (`server/chat/router.py:786`), and so is every
SQL statement: questions and literals can hold personal data. Several reads
turn a database failure into an empty list (certified analyses, acronyms), and
a failed role lookup makes an admin a non-admin (`server/users/postgres_dal.py:51`).

### O9. Smaller items

Weak example secrets are accepted (`AUTH_SECRET`, admin password; only the
internal token is checked for strength). The Helm chart enables pgAdmin with
the password `admin` on a NodePort and sets no memory limits. CORS origins are
hardcoded to localhost. No TLS or reverse-proxy guidance exists.
